# Pi 模式（团队 / 协同）

**消息发错 / 要重发**：如果用户说这条消息发错了、或者要重新发，并把消息给你，不要重新派单；直接调用 `/pi:steer <消息>`，把这条消息发给正在跑的 Pi。

**所有提问都用 `AskUserQuestion`**，不要用文字问；拿到答案就在同一轮继续。

## 模式（先问）

如果用户直接说明要让**多个 Pi** 一起完成，不要再问团队还是协同，直接按**多成员**走。

否则用 `AskUserQuestion` 问「开启哪个模式？」：协同模式 / 团队模式。

- **团队模式**：Claude 定计划、派单、审核；Pi 写全部核心代码，Claude 只做小修补。
- **协同模式**：两边平级；Claude 定文件分工，两边同时写；Pi 写完汇报；文件冲突由 Claude 提出。

模式只记在本次对话里。两个模式共用一个 `.pi-start-task.txt`，只能开一个。

## 分工（两种模式共用）

- Pi 的子代理自己派，Claude 不指挥。
- Pi 写代码的时候 Claude 可以派只读子代理做代码审核和文件架构分析。
- 审核必须自己看 diff 和代码，不能转述结论。
- 一个工作区只能跑一个 Pi；一个 Pi 只归一个 Claude 对话；多成员用多个工作区/目录。

## 0. 工作区

1. 需求里有路径（`~/...`、`/...`、`./...`）→ 用它。
2. 当前目录是 git 仓库，且不是 `$HOME` → 用它。
3. 判断不出 → 用 `AskUserQuestion` 问「在哪个目录做？」：选项给「当前目录（`<cwd>`）」和「取消」，Other 输入绝对路径。

确定后 `cd <工作区>`，后续命令都在这里执行。禁止把 `$HOME` 当工作区。

## 1. 计划 + 任务书

调用 `EnterPlanMode`，用户批准前不写代码、不派单。计划必须写清：

- 工作区（绝对路径）、目标（可验收）。
- 编号步骤，每步一个能单独验证的产出。
- 每步改哪些文件/接口；拿不准的点标出来。
- 风险与验证方式（具体命令或测试）。

**协同模式额外要求**：计划里必须有「文件分工」——哪些文件归 Pi、哪些文件归 Claude，两边不重叠；拿不准的文件先列出来问用户。

### 多成员（默认不启用）

默认只派一个写手。只有用户明确要求「多成员」时才考虑，且必须先有完整计划书：

- 目标与非目标；
- 文件/目录归属表，成员之间不重叠；
- 每个成员的 worktree 或独立目录、任务书、验收命令；
- 合并顺序、冲突处理、回滚。

计划书不全、归属重叠、或用户未批准 → 拒绝多成员，退回一个写手。上限 5 个成员，每个成员一个独立工作区；同一目录仍然只能一个 Pi。

无工作区/从零生成（如 10 个不同风格的网页）：允许 2–5 个成员，各建 `pi-team/<n>/` 目录；计划书先写风格矩阵，每个成员只写自己目录，Claude 汇总并查重风格。

用户批准后，**立刻**把计划写进工作区的 `.pi-start-task.txt`：

```
【角色】我是 Claude，你是本项目的秘书，核心编码全部由你完成，我负责计划与审核。
【要求】
1. 按下面的计划实现；子代理由你自己派遣（pi-subagents），不用等 Claude 指令。
2. 每完成一步，立刻汇报：怎么实现的、改了哪些文件、关键 diff 位置。
3. 全部完成后输出：改动文件清单、实现思路、如何验证、剩余风险。
4. 计划里没写的改动不要做；要偏离计划先停下说明原因。
5. 不能暂存、不能推送：禁止 `git add`、`git push`。
【计划】
（用户批准的完整计划，原样贴进来）
【需求原文】
（用户原始需求）
```

协同模式的任务书用这一份（文件名不变，还是 `.pi-start-task.txt`）：

```
【角色】我们是协作模式：你和我平级，都写代码。我定文件分工，你只改你那份。
【要求】
1. 只改「归你」的文件；「归我」的文件不要动。
2. 写完立刻汇报：改了哪些文件、关键 diff、怎么验证。
3. 要动我的文件、或发现冲突，先停下告诉我，不要自己改。
4. 不能暂存、不能推送：禁止 `git add`、`git push`。
【文件分工】
归你（Pi）：...
归我（Claude）：...
两边不重叠。
【计划】
（用户批准的完整计划）
【需求原文】
（用户原始需求）
```

## 2. 准备分支

先问用户：

- **不是 git 仓库** → `AskUserQuestion` 问「这个目录不是 git 仓库，要创建吗？」：选项「创建（pi/team）」/「不创建，直接改」。
  - 创建 → `git init -b pi/team`，把当前目录（排除 `.pi-*`）提交为 `baseline: before pi task`；提交失败就停。
  - 不创建 → 不走 git；后面所有 git 步骤跳过，直接改文件。
- **已经是 git 仓库** → `AskUserQuestion` 问「要新建/切换到 pi/team 分支吗？」：选项「新建/切换 pi/team」/「不建，就在当前分支改」。
  - 同意 → 切到 `pi/team`，没有就新建；切不过去就贴错误停。有未提交改动 → 提交为 `wip: before pi task`（排除 `.pi-*`），提交失败就停。
  - 不同意 → 留在当前分支，不提交，直接改。

提交只在本地，绝不 push；用户同意建仓库/分支时按第 6 节本地提交，否则不提交。

## 3. 派单 + 绑定

先看这个对话有没有绑定记录：

```bash
jq -e --arg sid "$CLAUDE_CODE_SESSION_ID" 'has($sid)' "${CLAUDE_PLUGIN_ROOT}/pi-bindings.json" >/dev/null 2>&1 && echo "ALREADY_BOUND"
```

- 有 `ALREADY_BOUND` → 用 `AskUserQuestion` 问「这个对话已经有绑定了，怎么处理？」：选项「当前目录有绑定就继续用」/「直接新建」。
  - 继续用 → 当前工作区有同目录绑定才传 `bind`；没有就传 `new`。
  - 新建 → 传 `new`。
- 没有输出 → 直接继续下面的问题。

用 `AskUserQuestion` 问「这次是新建 Pi 会话，还是绑定已有会话？」：

- **新建** → 第二个参数传 `new`，直接启动一个新的 Pi 会话。
- **绑定已有** → 调用 `/pi:connect` 命令（不要在这里重写列会话/绑定逻辑）；看到 `BOUND` 后回来，第二个参数传 `bind`。

陌生仓库先用 `AskUserQuestion` 确认「允许加载本地扩展吗？」（继续 / 取消），取消就停。

运行这条命令：新建会话时由 Pi 生成 ID，broker 用 `get_state` 拿到会话文件；用旧会话时直接拿绑定里的 ID 恢复。broker 以 `pi --mode rpc` 常驻，拿到会话文件后写绑定并输出 `BOUND=`。**看到 `BOUND=` 才算成功**；`BAD_TASK_MODE` / `NOT_BOUND` / `NO_SESSION` / `ALREADY_RUNNING` 就贴出来并停。

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/pi-dispatch.sh" "<工作区>" "<new|bind>" "start"
```

## 4. 等 Pi 结束

Pi 跑着的时候要纠偏用 `/pi:steer <指令>`，要停用 `/pi:abort`；不要重复派单。

用 Bash 的 `run_in_background` 跑这一条，收到退出通知再进第 5 步：

```bash
while [ ! -f .pi-done ] && kill -0 "$(cat .pi-pid 2>/dev/null)" 2>/dev/null; do sleep 2; done; echo PI_DONE
```

多成员：对每个成员目录各跑一遍，不要只在主工作区等：

```bash
for d in pi-team/*/; do (cd "$d" && while [ ! -f .pi-done ] && kill -0 "$(cat .pi-pid 2>/dev/null)" 2>/dev/null; do sleep 2; done); done; echo PI_DONE
```

协同模式：派单后你先写自己负责的文件；Pi 在后台跑，收到 `PI_DONE` 再复核 Pi 的文件和冲突。

## 5. 审核

1. 读工作区的 `.pi-events.jsonl`：`message_end` 里 assistant 的 text = 汇报；`tool_execution_end.result.structuredContent` = 命令输出与退出码。末尾的 `delegate_done` 是收尾标记：`status` 为 `completed` / `aborted` / `failed`，`error` 非空就是 Pi 报的错。如果最后一条 assistant 的 `stopReason` 是 `error`，把 `errorMessage` 原样贴给用户并停，不要继续审核。
2. 走了 git：跑 `git status --short -- . ':(exclude).pi-*'`、`git diff --stat`、`git diff`；有 `wip: before pi task` 就对照它，没有就只看 Pi 汇报的文件。没走 git：按 Pi 的汇报逐个读改动文件，跑项目测试。
3. Read 关键文件确认逻辑真的实现（不是注释、占位、假数据）。
4. 查：功能是否实现、是否删了原逻辑或吞异常、是否有计划外改动、声称的测试是否真跑过。
5. 协同模式额外查：Pi 是否只改了自己那份、有没有越界、接口/文件有没有冲突；有冲突你先提出来。

## 6. 返工 / 收尾

- 核心问题 → 返工单**追加**到 `.pi-start-task.txt`，直接执行第 3 节末尾的 bash：当前工作区有同目录绑定用 `bind`，否则用 `new`；多成员返工先 `cd` 到该成员目录。不要再走第 3 节的提问。
- 协同模式：返工单只写 Pi 负责的文件；你自己的文件直接改。
- 每轮修改后，若用户同意建仓库/分支，只提交到本地（绝不 push）。用户不同意则不提交。
- 小问题（拼写、格式、非核心架构问题）→ 自己改，报告注明「这部分由我修补」。
- 通过后：用户同意建仓库/分支才提交到 `pi/team`（排除 `.pi-*`，提交信息 `fix: <简述>`，不要 `git add -A`）；没同意就跳过提交，直接汇报。
- 收尾后，用 `AskUserQuestion` 问「是否开启审查模式？」：是 → 不用删旧绑定，直接调用 `/pi:review` 命令，新建一个干净的 Pi 会话审查；否 → 进第 7 节汇报。

## 7. 汇报

- 结论：成功 / 部分完成 / 失败
- 模式：团队 / 协同；协同模式附文件分工和各自改动
- Pi 做了什么（按步骤，每步一句）
- 实际改动（文件 + 增删行数，以 diff 为准）
- 审核意见（通过 / 问题清单 / 我修补了什么）
- 风险与未完成项

## 禁止

- 团队模式：替 Pi 写核心代码；协同模式：改 Pi 负责的文件、让 Pi 改你负责的文件
- 不看代码就转述 Pi 的结论
- 没有 `BOUND=` 就往下走
- 同时开两个 headless Pi 写同一会话
- 计划未批准就开工（说「直接干」除外）
- 指挥 Pi 的子代理
- 用户选了分支后还在 main/master 上改动或提交；用户没同意建仓库/分支时 push
